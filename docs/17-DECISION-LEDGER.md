# 17 — Decision ledger

**Append-only.** One row per decision. The owner's words are quoted verbatim where
they decided something — a later slice must be able to see which decisions were his
without re-litigating them. Never edit another landing's row; add a new row that
supersedes it.

Status vocabulary: **binding** (the owner decided) · **open** (not decided; a
successor must ask) · **superseded** (row N replaced it).

| 1 | **This project runs under the chief-of-staff process** — one dispatcher session (intake → scope → brief → dispatch ≤2 writers → verify → retire → report), writers in their own worktrees, every landing verified by the dispatcher. Owner, verbatim (2026-09-27): *"Please be my chief of staff. Project is empty, lets talk about it once you are settled."* The portable form of the process is Campaigner `docs/22-DEVELOPMENT-PROCESS.md`; this repo's `AGENTS.md` (next slice) is the binding local copy. | `AGENTS.md` (pending), `docs/20` | The role is host-global (`~/.dsh/AGENTS.md` §Chief of staff) and was designated directly. | 2 | **Intent: a flexible, anywhere-reachable store with grantable limited permissions.** Owner, verbatim: *"I want to make a flexible store that i can access from anywhere and where i can grant limited permissions. Details TBD."* | — | This is INTENT, not design: the mechanism is the dispatcher's to propose and the owner's to ratify. | binding |
| 3 | **It deploys on THIS box, using this box's disk.** Owner, verbatim: *"It should deploy here, on this box, using the disk space that we have here. It probably needs to be a server, but that is TBD."* Measured reality: `/dev/vda1` has **506 GB free (13% used)**; deployment seam on this host is `systemctl --user` with `Linger=yes`, loopback-bound, behind the existing cloudflared tunnel (precedent: `apps-web.service`, `dsh-web.service`). | — | "Server" is TBD, but the deployment target is not: a user unit + loopback port + tunnel ingress is how every service on this box is exposed. | binding (server shape open) |
| 4 | **Durability class: scratch / transfer space — local disk is enough.** Owner-selected 2026-09-27. No backup machinery, no checksum ceremony in the first slices. **FLIP CONDITION (written down so it is not lost):** the moment any store holds the ONLY copy of something an app or a person depends on, that store needs its own durability class (backup target + a restore test) — the dispatcher flags it at that moment rather than retrofitting it after a loss. | — | The owner chose the cheaper class knowingly; re-arguing it is churn. The flip condition is what keeps the choice honest. | binding |
| 5 | **The payload is a COLLECTION OF STORES, not one store.** Owner, verbatim: *"Depends on permissions. This should be scopable. For example, i would like to use this as a store for one specific app that needs shared data, permissions per user would than only be for that data store and format. I also want to be able to use this for arbitrary data. I guess, in reality, this should be a collection of stores with the ability to easily add new ones."* Consequence: the core (transport, auth, grants, storage) is built ONCE and a "store" is a declared instance (name + kind/format + its own grants); adding one is cheap. | `docs/18` (pending) | This is the seam the whole project hangs on: every later feature is either core or a store kind, never a third mechanism. | binding |
| 6 | **Sharing is by access keys, LLM-style.** Owner, verbatim: *"Lets use access keys similar to LLM keys."* Consequence: opaque prefixed keys, shown once at creation, **stored hashed at rest**, scoped to a named store with explicit permissions (read/write/delete/admin), labelled, optionally expiring, revocable, with `last_used_at`. Rotation = create new + revoke old. | — | Matches how the owner already reasons about credentials, and makes "limited permissions" concrete: the key IS the principal and the limit. | binding |
| 7 | **Exposure method is OPEN** — the owner asked for the implications rather than choosing: *"We need to discuss this. I am not aware of the implications and problems."* The dispatcher owed him the tradeoff in plain terms before any ingress is added. | — | A public hostname is a security perimeter decision, not a technical detail; it is the owner's to make once the implications are stated. | open |
| 8 | **Principals are OPEN** — whether the "users" who receive limited permissions are (a) apps/scripts holding a key, (b) end users of a host app who need identity inside one store, or (c) both. The distinction decides whether this project needs an identity subsystem at all, or only key management. | — | Misreading this builds a login system nobody asked for, or omits identity that a store genuinely needs. | open |
| 9 | **The public API surface is a door kept closed until an off-box client exists** (dispatcher recommendation, pending owner ratification under row 7). Build loopback/tailnet-first with key auth; opening the public route is then an additive ingress line, not a redesign. | — | Nothing to gain, and an internet-facing endpoint to be scanned, before a client actually needs it. | open |
